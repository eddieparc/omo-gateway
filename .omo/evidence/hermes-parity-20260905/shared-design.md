## 2. Actor ownership, identity, durable ingress (U13-U26)

### Chosen API and ownership

Keep one actor per canonical conversation. Add typed actor controls and durable acceptance replies rather than permitting command SQL writes. Introduce a small execution-store boundary using the existing SQLite pool; backend can checkpoint binding/submission through it but cannot overwrite SessionState. Actor applies acknowledged checkpoints to its own state. No SQL transaction is held across RPC, attachment download, or platform HTTP.

`route(event)` succeeds only after a SQLite acceptance transaction commits. The mailbox carries the durable event ID, not the only copy of the payload. The transaction inserts the session if needed, allocates a per-lane monotonic sequence, inserts immutable raw event JSON (UUID, all platform constituent IDs, attachments, source timestamp, sender, reply anchor, bot), claims constituent dedup IDs, and records queued state. Reserve/check the 64-entry capacity in this transaction; overflow is an explicit rejection before acceptance. DB errors refuse work, not log-and-run. Existing HTTP 202/Discord cursor advancement follows this commit. Hydration has a separate checkpoint so raw attachment metadata survives a crash during download; recovered inputs bypass split debounce. U22/U23 persist each admitted raw constituent and its bot-scoped dedup claim BEFORE debounce/cursor advance. Sealing a batch atomically assigns its ordered constituents to one logical event; an unsealed batch is sealed from its stored constituents on recovery, never merged with new live arrivals. The 64-slot cap counts pending logical events plus unsealed batch reservations, excluding the active event. A rejected capacity claim does not consume dedup IDs or advance the accepted cursor. After commit a failed mailbox notification leaves accepted work queued; wake the durable drainer, do not return a false rejection that encourages a new event identity. Source cursor may advance over durably rejected/admitted records, never an unclassified metadata failure.

Canonical Discord lane is bot + guild + actual channel/thread, independent of guild author; DM also retains peer identity. Keep the existing length-prefixed encoding; U17 adds its strict inverse parser (src/models/session.rs currently has only storage_key, no parser). Use the fixed user component `shared-guild` at both guild ingress and slash construction; this cannot collide with numeric Discord author IDs. Preserve real sender separately in event metadata. Parent channel is routing metadata, not egress target. Full serialized SessionKey accompanies rows; never reconstruct bot identity from channel columns. Cron execution identity is profile/job/run, never destination user or numeric job ID interpreted as channel.

Legacy identity cutover is non-destructive: record aliases to original rows, never concatenate independent OMO histories. If exactly one populated old guild lane exists, adopt its binding into the new canonical lane. Multiple populated old author lanes require an explicit selected predecessor before that lane accepts work; retain all historical rows and fail continuity visibly rather than guessing newest. Missing bot identity requires an unambiguous configured mapping or quarantine. Existing DM keys and exact-bot obligations remain unchanged.

### Durable execution state machine

Store event state, session revision/generation, remote binding and remote turn ID separately from presentation state:

`queued -> preparing -> submit_intent -> accepted_remote -> execution_completed -> delivery_pending -> delivered`

Other terminal/non-replay states: `silent`, `failed_pre_submit`, `interrupted`, `execution_unknown`, `continuity_error`, `cancelled_queued`. Execution completion and delivery are independent columns/states, not a single success boolean.

- Persist new thread binding immediately after thread/start ACK, BEFORE turn/start. Failure to persist prevents turn submission. Missing rollout on resume is continuity_error, not automatic fresh history. Unbound remote thread created before crash can be orphaned without replaying a turn.
- Persist submit_intent **before attempting the socket write**. Once that write might have begun, any crash/disconnect without definitive outcome is execution_unknown. clientUserMessageId is supported identity metadata, NOT an idempotency contract; never submit again automatically, even if turn/start ACK was not received. A crash between the intent commit and the actual write is deliberately conservative unknown unless another durable fact proves no submission.
- On ACK persist exact remote turn ID. After gateway-only crash, read/resume that thread and reconcile that exact turn only. A proven terminal result can be committed; a running turn can be interrupted/observed, but is not re-executed. Installed threads/turn-log.js stores turns in a process-local Map; wire-thread.js reconstructs fallback history with synthetic turn-N IDs, completed status and no original client ID. After daemon restart these reconstructed records are NOT authoritative terminal receipts. Never match synthetic IDs, timestamps, prompt text or last assistant row to infer success. Missing exact original turn evidence leaves execution_unknown. Experimental history-list APIs cannot restore guarantees their source lacks.
- Only queued/preparing/proven-before-write failures are automatically retryable. Recovery retains sequence and eligibility through failed routing and a second crash. An uncertain head blocks later work in the same lane until remote idle is established and uncertainty is explicitly resolved; other lanes continue. Queued B must not overtake ambiguous A on a still-running remote thread.
- Commit assistant transcript (deterministic result ID), terminal execution record, actor state revision and outbound obligation(s) in one SQLite transaction. Failed commit emits no delivered status and causes no engine rerun. Transcript dedup never treats a user row alone as evidence of completed execution.
- `/stop` preserves binding and history, cancels queued events explicitly, interrupts actual remote work, and marks suspended. Successful stop means acknowledged interrupt and verified idle/terminal, not socket close. Unknown interrupt outcome is reported as such and lane remains blocked. Shutdown preserves queued work instead of cancelling it as a user stop would.

Reject: resume_pending + latest-user-row replay loses accepted queue identity and can duplicate mutations. Reject: backend mutating shared SessionState or SQL after actor clone creates stale overwrite races.

### Control transaction

Add `Multiplexer::control(key, Control) -> ControlResult` and ActorCommand::Control with a oneshot result. State controls queue in the same lane order as events; steer and stop target the active generation immediately. Actor remains sole SessionState writer. A durable control intent carries operation ID, expected revision, binding/generation, requested change and phase; mark sent before remote mutation, then commit local projection only on authoritative success. Unknown outcome is not success and never blindly repeats a non-idempotent mutation. This is a journaled protocol transaction, not impossible atomic SQL+RPC.

| Control | Minimal supported semantics |
|---|---|
| model/effort | Idle serialized settings/update; ACK then commit actor revision. Absolute set can be reconciled by reading effective settings; no stale final flush restores old value. |
| steer | Active acknowledged turn only, exact expected turn identity per installed parser; no new user turn/turn-start. Idle returns no-active-turn. Persist the steering audit record, not a duplicate normal inbound row. |
| reset | Explicit user reset is the only normal binding rotation: after active work is stopped/idle, start fresh thread in same agent resources, atomically publish new generation/binding and clear local visible conversation/session grants. Preserve archived old transcript and outbox receipts; old final cannot land in new generation. |
| undo/retry | Unsupported on this installed peer because no rollback contract is registered. No local deletion/re-appending as a substitute. Future supported retry requires successful rollback first and a new explicit operation ID; it is not automatic crash replay. |
| compress | Send compact/start while idle; wait for the matching contextCompaction started/completed item, or reconcile its turn-log outcome. Timeout/failed compaction returns unknown/failed, never a fabricated local summary. Do not erase canonical raw transcript. |
| yolo | Retain existing persisted state, restore guard from actor state on load, toggle through actor; reset clears state and guard together. Hardline/deny and deadline remain above bypass. |

2. U51 identifies and unloads matching launchd service BEFORE residual verified-process signals; quiesce source including in-flight job writers and acquire all selected store locks in sorted canonical path order. Failure leaves sources intact and reports service state; no blind PID signal or automatic service restart on partial error.
3. Under locks take final snapshot of ALL stores; revalidate against planned canonical content, not just IDs. Changed payload requires re-import/revalidation under locks before continuing. Prepare private backups and empty replacement files for all stores before first source rename.
4. Commit receipt journal + exact imported rows as cutover_pending in one SQLite transaction. Journal includes operation ID, complete store set, original and replacement hashes, backup paths, normalized job digests, policy/config digest and per-store phase. No destination execution yet.
5. Replace each source with prepared empty document using U50 primitive; record progress. Revalidate bytes before each replacement. Crash/error leaves durable incomplete receipt and both runtimes quiesced. Startup refuses scheduling/full success until recovery reconciles every store's bytes against original/replacement hashes. Recovery completes the recorded cutover, never silently guesses or starts both engines; unknown external edits require operator resolution with backups preserved.

An all-store rollback on ordinary error is permissible only as an explicit journaled recovery operation restoring ALL verified originals while destination remains disabled; do not promise immediate all-or-nothing filesystem rollback across power loss. Minimal automatic recovery chosen here is roll-forward from verified prepared receipt. Import-only never retires source or changes authority to omon_owned.
